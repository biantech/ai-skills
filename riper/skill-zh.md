# RIPER-5 中文参考说明

这份文件是 `/Users/bianjq/.augment/rules/augment-guidelines.md` 的中文精简备份，供 `riper` Skill 参考。实际执行时，以用户请求、当前 `AGENTS.md` 和 [SKILL.md](SKILL.md) 为准。

## 一、适用目标

RIPER-5 用于复杂工程任务，例如架构调整、迁移、认证或支付改造、多文件重构和高风险数据处理。它将工作分为研究、构思、规划、执行和审查五个阶段，避免在证据不足时直接修改代码。

简单的拼写修正、明确的单文件小改动和一次性原型通常不需要完整执行五个阶段。

## 二、核心原则

- 从整体架构、调用链和依赖关系分析到具体实现。
- 同时考虑多种方案，比较正确性、兼容性、维护成本和风险。
- 让分析深度与任务风险匹配，优先提取能影响决策的事实。
- 保持理论分析和实际验证一致，不根据猜测替代可验证事实。
- 遵循现有架构和编码风格，避免无关重构。
- 每个改动都应能追溯到用户需求或验证结果。

## 三、五个阶段

### 1. 研究 Research

目标是建立可靠的事实基础。

- 读取相关的 `AGENTS.md`、实现、调用链、配置、接口和测试。
- 检查 Git 状态，保留用户已有的未提交修改。
- 明确当前行为、目标行为、约束、依赖、风险和未知信息。
- 需要真实数据时使用权威工具，不根据代码推测数据库记录。
- 研究阶段只读，不修改实现文件。
- 输出观察结果、问题和证据，不输出内部思考过程。

### 2. 构思 Innovate

目标是比较可行方案，而不是立即写代码。

- 提出两个或三个可信方案，或说明为什么只有一个合理方案。
- 比较正确性、兼容性、可维护性、实施风险和验证成本。
- 优先使用现有架构、工具和依赖。
- 给出推荐方案及关键取舍。
- 方案明确且简单时可以跳过此阶段。

### 3. 规划 Plan

目标是形成可执行、可验证的技术计划。

- 列出涉及的文件、模块、类、方法和组件关系。
- 说明行为、接口、数据结构和配置变化。
- 说明异常处理、兼容性、迁移和回滚策略（如适用）。
- 明确测试、静态检查、构建或数据验证方法。
- 将计划拆成有顺序的原子步骤，并定义成功标准。
- 复杂任务在修改前先展示计划；小任务可在进度说明中简要记录。

### 4. 执行 Execute

只有用户请求授权修改时才执行。

- 按已确认的计划实施，遵循仓库现有风格。
- 只修改必要文件，不添加未请求的功能。
- 先导入依赖，再使用依赖；不引入未经验证的依赖。
- 不使用占位符，不留下不完整实现。
- 对非显而易见的逻辑添加简洁注释。
- 每完成一个阶段就运行匹配范围的验证。
- 如果新证据使计划失效，先说明原因，再返回研究或规划阶段调整。

未经用户明确要求，不创建分支、任务文件，不暂存、提交或推送代码。

### 5. 审查 Review

目标是确认实现符合需求和工程约束。

- 检查最终 diff，确认没有无关文件变化。
- 检查边界条件、异常处理、兼容性、安全影响和可维护性。
- 运行与改动风险匹配的测试、Lint、构建或专项命令。
- 明确报告失败项，并区分代码缺陷和环境限制。
- 对代码审查按严重程度报告问题，并提供文件和行号。
- 说明是否完成用户要求，以及仍存在的风险。

## 四、阶段切换

原 Augment 规则使用以下信号切换阶段：

```text
ENTER RESEARCH MODE
ENTER INNOVATE MODE
ENTER PLAN MODE
ENTER EXECUTE MODE
ENTER REVIEW MODE
```

在 Codex 中，阶段是检查点而不是无条件的权限门槛。用户明确要求实现时，可以按研究、构思、规划、执行、审查顺序连续推进；用户只要求分析、规划或审查时，在对应阶段结束。需要用户选择或确认的重大取舍必须停下来询问。

## 五、沟通和代码规范

- 默认使用中文交流。
- Yuanchuan 项目的业务说明和 Swagger `@Schema` 描述使用繁体中文。
- 日志、代码标识符和代码注释以英文为主，避免无必要的特殊字符。
- Python 使用标准 `logging` 输出运行信息，不用 `print` 代替日志；日志应在当前控制台可见。
- Java 的 `log.info` 信息以英文为主。
- 遵循项目现有 DDD 分层和测试约定。
- 代码块应标注语言；说明修改时提供必要的文件路径和上下文。
- 不展示内部思考过程，只输出可验证的结论、计划、决策和结果。

## 六、任务记录模板

复杂任务可以在用户指定的位置记录以下内容；不要自动创建任务目录或任务文件：

```markdown
# 背景

# 任务描述

# 项目概览

# 分析

# 提议的解决方案

# 当前执行步骤

# 任务进度

# 最终审查
```

任务记录应包含时间、已修改文件、变更摘要、验证结果、阻碍因素和当前状态。

## 七、与原始规则的适配说明

以下内容不作为 Codex 的强制行为：

- 固定声明“你是某个特定模型或 IDE 中的代理”。
- 强制每次输出模式声明或内部思考过程。
- 未经用户请求自动创建分支、任务文件、提交和推送。
- 以固定响应时限作为工程质量标准。
- 要求展示完整代码而不是直接修改工作区文件。

这些内容会与 Codex 的系统约束、当前 `AGENTS.md` 或用户授权边界冲突，因此仅保留其背后的安全和流程意图。
